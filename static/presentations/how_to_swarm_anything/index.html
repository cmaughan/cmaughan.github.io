REPOSITORYthe shared model of reality

The interesting swarm problems are too large for one worker to understand at once. They cross subsystems, platforms, tools, and definitions of done.

The trick is not to give every agent more context. The trick is to arrange the repository so that each agent needs less context, while the finished pieces still compose into one product.

This is an architectural problem before it is a prompting problem.

The prompt is part of the codebase.

Every worker starts with the same map, rules, and definition of done.

Less private context. Fewer invented conventions.

The first artifact is the operating manual. AGENTS.md is not a welcome note. It records how work is chosen, where code belongs, which files are shared, how changes are validated, and what a clean handoff looks like.

That moves maintainer judgment out of private conversations and into versioned project state. Every worker begins with the same rules, and the rules evolve with the software.

Specific instructions beat vague encouragement. “Dependencies point down” and “new behavior gets a new module” are useful. “Write good code” is not.

ARTIFACT · architecture.md

Dependencies may only point downward.

check-layers enforces the rule. The diagram is not a suggestion.

A worker can own one region without learning the entire system.

Parallel work needs boundaries that a machine can enforce. The architecture document describes layers, allowed dependencies, public seams, and ownership zones.

A layer checker turns the diagram into a rule. A worker changing storage cannot quietly reach into the interface. A worker adding a command cannot bypass the domain model.

The architecture therefore does two jobs. It keeps the software clean, and it reduces the amount of context needed to make a safe change.

Ambition becomes a measurable backlog.

A swarm needs a finite description of the product it is trying to build. The surface catalog records every user-visible capability with a stable identifier.

Those identifiers join interface, engine, automation, documentation, and tracking. When an implementation registers the identifier, every client can discover it. When it is missing, the gap remains visible.

The catalog prevents a common failure mode: lots of locally impressive work with no reliable picture of whether the product is becoming complete.

Four clients. One behavior. One undo boundary.

The command registry is the central seam. A command carries its stable ID, parameters, precondition, implementation, result, and undo behavior.

Every client converges on that registry. The interface does not contain a second implementation. The automation layer does not invent another API. Recorded actions do not bypass validation.

This makes functionality composable. It also gives agents a small, typed place to discover and extend behavior.

Strategy becomes a queue. The queue becomes evidence.

The work queue belongs in the repository too. The roadmap says where the product is going. The gaps document ranks missing behavior. Machine-readable scorecards attach status, evidence, and budgets to individual capabilities.

A worker can choose useful work without a meeting. More importantly, the same worker updates the evidence when the change lands. CI regenerates reports and rejects stale claims.

This keeps the swarm aimed at user value rather than whatever task happens to be easiest to prompt.

There is no magical conductor in the middle. The repository coordinates the swarm.

Workers use isolated workspaces, claim narrow file sets, add behavior in new modules, and keep edits to shared registries small. The shared artifacts tell each worker what matters and what finished means.

This looks more like a distributed system than a group chat. Workers do not need identical knowledge. They need stable contracts, low-conflict write paths, and a reliable shared state.

The unit of parallel work is a vertical slice, not a broad layer. A useful slice starts with one visible gap, adds one command, reuses or extends a lower-level capability, proves success and failure, and updates the evidence.

That shape is easy to review and easy to merge. It avoids the swarm failure where one worker builds a framework, another builds an interface, and neither quite matches the other.

Most files in the change are new. Shared registries receive only the smallest possible edit.

A bug report can become a runnable script.

Agents should be able to operate the software, not merely edit source and hope. A small control protocol exposes the command catalog, preconditions, state, bounded previews, and interface screenshots.

The tools use the same command path as the human interface. They do not create a privileged second application hidden behind the first.

This closes the loop: inspect, act, see, correct. It also makes bug reports executable. A reproduction can be a short command sequence rather than a paragraph about where somebody clicked.

Why Rust fits the framework

Rust
One languagedomain, native UI, CLI, automation, web build
Explicit seamstypes make architectural boundaries harder to blur
Local reasoningownership exposes sharing and mutation
Native speedparallel CPU work and portable GPU compute
Portable coredesktop platforms and WebAssembly

The framework does not require Rust, but Rust reinforces its ideas unusually well.

Types make command and layer seams explicit. Ownership makes sharing and mutation visible. Errors are values rather than hidden control flow. The domain, native interface, command-line tools, automation server, and browser build can live in one language and one workspace.

Rust does not make correctness automatic. It does make many accidental forms of architectural drift harder to introduce across agent boundaries.

Tests and measures, not trust

MEASURES · HOW GOOD IS IT?
Perf budgetsnamed scenarios with targets; regressions fail
Size gatethe web build must stay under its limit
Coverage floorthe count of live commands can't go down
Scorecardgenerated from evidence; CI fails if it's stale

Every change also passes format · lint · layers · cross-target builds

The swarm expects workers to make mistakes, so quality has to be checked by machines, not assumed. There are two kinds of check.

Tests answer “does it behave?”. Every crate has unit tests, with property tests generating inputs for the trickiest data structures. File formats get byte-exact round trips, and hostile input: files truncated at every offset, plus fuzz targets for the parsers that run in CI. Real-world files live in pinned, checksum-verified corpora, and the pass counts have floors that can’t drop. A render oracle compares the compositor’s output with the image the file itself embeds. And a set of realistic agent tasks drives the app through the control API and checks the result by screenshot.

Measures answer “how good is it?”. Performance scenarios each have a budget; anything not yet met is tracked, and regressions fail. The web build has a size gate. The count of live menu commands has a floor. The scorecard is generated from all of this, and CI fails if the committed copy is stale.

Underneath, every change passes formatting, lint with warnings as errors, the layer checker, and the cross-target builds. Workers run the narrow checks while they iterate, and the full relevant set before they hand off.

Swarming can produce astonishing breadth quickly. That makes honest maturity tracking essential.

The scorecard separates existence from depth. A command may be wired and reachable while its edge cases, performance budgets, platform coverage, or recovery paths remain incomplete.

That is useful information, not an embarrassment. It prevents feature counts from being mistaken for readiness and gives the next wave of workers something concrete to improve.

The most useful single file turned out to be a ledger of my decisions. One line per direction, each dated, newest decisions winning.

Agents read it alongside AGENTS.md. If the two disagree, the more recent direction wins and AGENTS.md gets fixed. There’s a small revision table at the bottom, so you can see how the direction changed over time.

The important habit is that the agents maintain it. When I make a call in a conversation, it becomes a line in the file, so the next worker, who never saw that conversation, still knows.

Steer with decisions, not prompts

01The swarm writes a planwith numbered recommendations and open questions
02I answer the questions“all eight recommendations approved”
03Answers become directionsone dated line each, in the ledger
04The plan becomes ticketsphases filed, in whatever order makes sense

My job became answering good questions, not writing prompts.

Big pieces of work started as a plan written by the swarm, not by me. Each plan ended with numbered recommendations and a short list of questions only the owner could answer.

I answered them, sometimes in a sentence: all eight recommendations approved. The answers went straight into the ledger, and the plan was split into tickets.

That changed what my day looked like. Less prompting, more product management: deciding, approving, and setting the quality bar.

A golden reference beats a spec

THE RULE

Do what the original does, unless there is a reason not to.

Accessibility is a reason. Taste is not.

Match, don't exceeda menu item the original never enables stays disabled
Use it as an oraclecompare results event by event through its own API
Read it for gotchasits source knows how real apps misbehave
Never modify itstudy it, run it, never change it

A spec is never complete, and agents fill the gaps with their own ideas. A working product to copy is much better.

The rule was simple: do what the original does, unless there’s a real reason not to. Accessibility was a good reason; we kept a few contrast fixes. Personal taste was not.

Match it, rather than going beyond it: if the original never enables a menu item, ours doesn’t either. Use the original’s own scripting API as an oracle to compare results event by event. Read its source for the ways real applications misuse the API. And never, ever modify the reference install.

Toy targets mislead

THE TOY
One tiny demo app
  • Every feature worked on it
  • Tests run 20 times over
  • The code bent around its quirks
→
THE REAL WORLD
Public sample suites
  • Dozens of real applications
  • Run once, twice to confirm a fix
  • Failures point at real gaps

The early focus on the toy was too invasive. Real workloads drive the work.

Early on the swarm leaned hard on one tiny demo application. Everything worked on it, tests were run over and over, and the code started bending around that one app’s quirks.

I redirected the work to public sample suites: dozens of real applications. Repeated runs stopped too; once, then twice to confirm a fix, and leave the rest to CI.

The toy is still useful for testing a mechanism. It just isn’t representative, and a swarm will happily optimize for whatever target you hand it.

How work moves through the swarm

Issueranked in the tracker
Claimlabel + comment
Worktreeone per worker
MRwith a Progress section
Local gatethe full check, on real hardware
Mergeby the coordinator
Workersclaim an issue, build it in their own worktree, open an MR, clean up when it closes
Coordinatorstarts workers, merges on a green local gate, watches main, stops merging while it's red

The process settled into a simple pipeline. Issues are ranked in the tracker. A worker claims one by adding a label and a comment, builds it in its own worktree, and opens a merge request.

The coordinator merges on a green local gate, run on real hardware, rather than waiting for a CI pipeline. It then watches main’s pipeline and stops merging while it’s red.

One lesson here: the coordinator has to claim its own work too, however small. Otherwise a worker picks up the same issue and you get duplicates.

Shared files are merge magnets

WORKERS DON'T EDIT
ROADMAP.md
docs/roadmap.md
docs/gaps.md
Each MRcarries a Progress note: measured numbers, what moved, what's open
The coordinatorupdates the summaries once per batch

Every worker wanted to update the roadmap and the gaps list when it finished something. With several workers, those files became merge conflicts waiting to happen.

So workers stopped editing them. Each merge request carries a short Progress section instead, with the measured numbers and what’s still open. The coordinator rolls those up into the summaries once per batch.

For the same reason the issue tracker stayed the board, rather than a Kanban folder in the repository. With a Mac and a desktop PC both taking work, claims need shared live state.

It must stay small and never hold the swarm back.

Once there were several agents, I couldn’t tell what was going on by reading chat. So every agent, workers and coordinator, logs its sessions and its work on issues to a tracking branch: one small JSON line per event.

Workers log claim, work, submit, stop and release. The coordinator also logs merges and send-backs. Sessions record their role, their parent and the model.

The rule was that tracking must stay tiny and never slow the swarm down. This is real data, trimmed: one worker, one issue, about 25 minutes from claim to submit.

Waste is a metric

DUPLICATEOverlapping claimsthe work each duplicate threw away, and a redundancy figure
ABANDONEDWhy each span endedduplicate · released · blocked · sent back · dead agent
SENT BACKA state of its ownvisible on the board while the worker is still in session
STUCKDead, waiting, or active?the coordinator can close a dead session's claim

Credit goes to the merge that landed, not to the effort.

Once the waste was visible, it became something to measure and reduce.

Duplicate work shows up as overlapping claims, with the span each duplicate threw away and an overall redundancy figure. Abandoned work is labelled with why it ended. Sent-back work gets its own state on the board. Stale lanes are classified as dead, waiting or active, and the coordinator can close a dead session.

And credit is strict: a released or abandoned stretch only gets credit for a merge if its own merge request is the one that landed.

Capacity is measured, not guessed

3
workers per swarm
on one desktop
Ask firsteach worker checks capacity before its full gate
Zero means waitor check only what changed
Build vs read helpersread helpers are never refused for build load; at most 4 per worker
Heavy tests sparinglyslow tests once, twice to confirm; repeats belong in CI

The worker count came from measuring builds on the machine, not from a guess.

It’s tempting to keep adding workers. On one desktop, builds and heavy tests compete for the same cores, memory and devices, and past a point you just slow everyone down.

So capacity became a command with a measured rule, not a guess. Each worker asks it before running the full gate; if it says zero, the worker waits or runs only the checks for what changed. Helper sub-agents are split into build helpers and read helpers: readers are cheap and never refused, but capped at four per worker.

The measured answer was three workers per swarm on my desktop.

Rules written in pain

End what you launchno test apps, windows or crash dialogs left behind
Failures must be loudI hit a silent failure; now the UI must say so
Scrub what you spillno user or host names in output files
Clean up worktreesand their build directories, when the issue closes
Leave my checkout aloneit stays on main; agents work in worktrees
No dead controlsa control that does nothing on a tab isn't shown there

Many of the directions are rules I only wrote after something went wrong.

Test runs left windows and crash dialogs all over the desktop, so every test now ends what it launched. I hit a failure that the UI didn’t report, so failures must be visible. Output files contained user and host names, so they’re scrubbed. Worktrees and build directories piled up, so workers remove them when their issue closes. An agent switched my own checkout off main, so agents work only in worktrees. And controls that did nothing on some tabs got hidden there.

Risky code lives at named seams

DEFAULT
Safe code everywhere unsafe denied across the workspace
Approved modules onlyeach exception named, planned, and signed off by the owner
Every block justifieda SAFETY comment on each one; none in generated code
Decisions stay safelayout and ordering are decided in safe code above the seam
Only our own processeslaunch what we create; never touch a running one

Some code has to do risky things: call native APIs, talk to the OS, launch other processes. The rule was that unsafe code is denied everywhere by default, and each exception is a named module that I approve as part of a plan.

Inside those modules, every unsafe block carries a safety comment, and none appears in generated code. The decisions, like memory layout and ordering, are made in safe code above the seam. And the launcher only ever starts processes it creates; it never attaches to one that’s already running.

Environment traps

1Launched as administrator
2The app it started ran as administrator too
3That app ignored our environment settings
4Nothing connected, and nothing said why
THE FIXES
Launch with normal rightsas the original product does
Make failure louda target that crashes, exits or never connects must say so

Not every failure is in the code. One of mine was the environment.

Run as administrator, the tool launched its target as administrator too. An elevated process ignored the environment settings the tool relied on, so nothing ever connected, and nothing told me why.

The fixes were to launch targets with normal rights, as the original product does, and to make the UI report any target that crashes, exits or never connects. That second rule is in the ledger because of this.

Small decisions that paid off

Web from day onekeep the core browser-clean from the start
Borrow performance targetstake the numbers that transfer from the original's own code
Borrow the look and feelfamiliar to the original's users; small accessibility fixes kept for review
Defer on purposecode signing and CI runners waited, and the ledger says so
Ask the original's ownersan open question becomes a ticket for them, not a guess

A handful of smaller calls that turned out well.

Swarm B kept its core clean enough to build for the browser from day one. Performance targets that made sense were copied from the original product’s code, rather than invented. The look and feel follows the original, so its users feel at home, with a few accessibility fixes kept aside for review.

Some things were deferred deliberately, like code signing and CI runners, and the ledger records that, so nobody wastes time on them. Where the original’s behaviour was unclear, the swarm filed a question for the original’s owners rather than guessing. And merges happen on a green local gate rather than waiting for the CI queue, with merging paused whenever main goes red.

Never claim from a list you made earlier.

Claims race. In one swarm, four claims raced on a single day. In the other, the coordinator started an issue from a listing twenty minutes old, after another agent had already claimed it, and that work was thrown away.

The fix was one claim command that does everything at the moment you start. It checks the label, any open merge request, and live claims on the tracking branch. Then it creates the branch, the draft merge request, the label, the comment and the event. A handful of shared files cause most of the merge conflicts: the root build manifest, the command registry, the menus, the translation catalog and the architecture’s layer table.

Here’s the claim command in detail. It refuses if the issue already has the in-progress label, if any open merge request already names it, if another agent has a live claim in the tracking log from the last 24 hours, if the issue is blocked or closed, or if main is red.

Otherwise it does everything in one step: a branch from the latest main with an empty claim commit, a draft merge request from the template, the label, a comment, and the claim and work events. When a gate fails, the tool reads the log and classifies the cause. Three locks

Three locks keep the gates from hurting each other.

A per-repository gate lock means only one coordinator gates at a time; it’s shared by every worktree of the clone, and goes stale after two hours. A machine-wide lock, outside both repositories, means only one gate builds at once, whichever swarm it belongs to: one gate’s links alone held about 30 of the desktop’s 32 gigabytes. And the lock names its worktree, because twice a manual checkout swapped the tree out from under a running gate.

The build tool’s parallelism is set from free memory, one job per one and a half gigabytes. Docs-only gates skip the machine lock entirely: a docs fold that had waited ten minutes behind the other swarm’s gate then took a tenth of a minute.

My favorite small incident. An agent trimmed a noisy command by piping it through tail, then chained the next step with “and”. But a pipeline’s exit status is its last command’s. The stack command was refused, tail succeeded, and the gate ran anyway on the wrong tree.

It was caught only because every command checks its own preconditions instead of trusting the one before. The rule now is pipefail or no filter.

A related one: piping a long command through tail or head hides all its output until it ends, so a fifteen-minute full gate looks exactly like a hang. Agents now announce when they start one, and report the result.

Code health is enforced as a ratchet. Functions have hard limits: cognitive complexity of 10, 60 lines, six parameters.

Anything over a limit needs an explicit exemption with a reason, and the exemption itself fails the build once the code is fixed, so stale ones can’t linger. The tool prints the count per crate, and it can only go down: 95, then 90, now 84.

Every library also denies the panicking shortcuts, unwrap, expect, panic and todo, and forbids unsafe code entirely.

Bugs were 16% of issues: 37 bugs against 184 tasks. The median bug was fixed 63 minutes after it was filed, 90% within two and a half hours, slightly faster than the median task. None is open, and nothing has ever been reverted.

When I asked for a stable feature set, a stability sweep of every command and pane found eight defects, and all eight were fixed in under two hours; a second sweep found only small naming and layout issues.

Since merges started landing on the quick smoke gate, all four full gates of main have passed. And over six days, about one gate in ten failed, but none in the last 44 hours.

For: bugs are cheap here. They get filed and fixed in about an hour, the quick gate hasn’t let a defect reach main, and every incident has made the safety nets tighter. Most of the defects that slipped through were analytics showing wrong numbers, not lost data, and each fix came with a test that pins it.

Against: some defects lived a long time before anyone noticed, 35 to 58 hours of wrong statistics that I was reading in the meantime. Process bugs still cost real work: claim races threw work away five times. There’s no send-back rate yet, so how much rework “fix later” causes isn’t measured. And the evidence is thin: four full gates of main, all in about a day, while the sibling swarm went red twice in one day.

My answer so far: yes, as long as main stays green, bugs are treated as ordinary tickets, and the tool enforces the stop when something breaks. But this is a tool used by me, not a product with customers, and that changes the risk a lot.

A rule the tool didn’t enforce

A rule only in the docs broke within a day of being needed.

The rule said nothing merges while main is red. The claim command enforced its half: no new work. But the land command never checked, and in the sibling swarm, two merge requests landed while two red-main issues were open.

It was fixed the same day: land now refuses too, unless the merge request fixes the red issue or the coordinator gives an explicit reason, and both commands share one function for the check. The lesson is the same one as the whole appendix: a rule that only lives in the docs breaks the first time it matters.

Workers keep going

BEFORE
The coordinator starts each worker
  • A worker finishes one issue and stops
  • The coordinator has to notice and start another
  • It can only start sessions when the owner is around
→
NOW
Workers schedule themselves
  • After submitting, take the next unclaimed issue
  • Repeat until none is left, then stop and say so
  • The coordinator only fills empty slots and redirects by message

Originally the coordinator started every worker, one issue each. But the coordinator’s own harness only lets it start new sessions in turns that I begin, so while I was away, finished workers just stopped.

Now workers keep going. After submitting, a worker takes the next open, unclaimed issue, and repeats until there are none left, then logs that it stopped because there was nothing left. The coordinator only starts a worker to fill an empty slot, and redirects running workers by sending them a message.

One command to submit

1rebaseonto the latest main, or the MR below
2ci --changedon the rebased tree
3pushwith a lease, so nobody's work is overwritten
4mark readyrefused if Progress isn't filled in
5start CIthe MR's pipeline
6log submitthe event, for the timeline

The submit checklist became one command: ready.

Submitting used to be a checklist the worker had to remember. Now it’s one command. It rebases onto the latest main, re-runs the changed-scope gate on the rebased tree, pushes with a lease so it can’t overwrite anyone’s newer work, marks the merge request ready, starts its pipeline, and logs the submit. It refuses if the Progress section is still the template’s placeholder.

Rebasing before submit also takes load off the coordinator, which otherwise has to rebase stale branches itself. A send-back-rate measure is being built to check that.

Agents run stale tooling

THE PROBLEM
Each agent's build tool is as old as its branch
  • A worker ran main's full gate with its own, older tool
  • Changes to the gate took effect whenever agents happened to rebuild
→
THE FIX
Run main's own tool on main
  • The claimant only decides, races and checks out
  • Then hands over to the tool in the commit being gated
  • A gate change takes effect with the commit it gates

A subtle one. The process lives in the build tool, but each agent runs the build tool from its own branch, which can be days older than main. So a worker could run main’s full gate using an outdated version of the gate.

The fix: the claiming agent only decides that a full gate is due, wins the race and checks out main. Then it hands over to the tool built from the commit being gated. A change to the full gate now takes effect with the commit it gates, not whenever each agent happens to rebuild.

Hold the claim before the long check

WHAT HAPPENED
claiman agent started a claim, which ran a due full gate first
18 minthe issue looked free the whole time
raceanother agent took it; the first agent's work was thrown away
THE ORDER NOW
Hold the issue firstlabel, comment and event before anything slow
Then run the full gatethe claim is already visible to others
If main is redrelease the task's claim and take the red issue instead

Another claim race, from a new direction. When a claim found that a full gate of main was due, it ran the gate first and only then marked the issue as taken. For eighteen minutes the issue looked free, another agent claimed it, and the first agent’s work was thrown away.

The claim’s steps are now a planned order: hold the issue first, then run anything slow. If the full gate finds main red, the agent releases the task it was going to do and takes the red-main issue instead.

Gate the tree, not the branch

gatedtree 7c1e…passed
branch movedtree 7c1e…same tree
landtree 7c1e…landing

If the content is what was gated, a moved branch is fine.

Land restacks without a checkout and compares trees. Only a different tree is refused.

Land used to refuse any branch that had moved since it was stacked, which was safe but caused needless re-gating: often a branch had been rebased and its content was identical.

Now land restacks the branches in memory, without a checkout, and compares the resulting tree with the one that was gated. If they’re identical, it lands, and says so. Only a different tree is refused. It’s content-addressed verification: what matters is what was tested, not which commit pointer it hangs off.

Every gate now keeps its per-test timings, and a command compares them across gates to find the long poles.

Where we agree, where it hurts, where we disagree, and what we can't answer yet.

When I showed the design to another team, they summed it up in one line better than I had: the tracker carries the work, the tracking branch carries the record, and the build tool carries the rules.

That’s the whole architecture of the swarm’s process. None of it lives only in a prompt.

Where it hurts

The bottleneck movesonce nobody reads every line, merge, CI and special hardware become the limit
Coordination bugs are swarm bugsracing claims, a coordinator that skipped claiming, idle workers waiting on merges
Hard to see without a timelinenone of these showed up until the events were drawn

Not everything transfersa shared compile cache got zero hits across worktrees
A guess, untestedpast 4–5 machines, merge and test dominate, and more work gets redone

Comparing notes with other teams running factories, the pains were remarkably similar.

Once nobody reads every line, the bottleneck moves to merging, CI, and any tests that need special hardware. Coordination bugs are swarm bugs, and they were invisible until there was a timeline: racing claims, a coordinator that decided it didn’t need to claim tickets, workers sitting idle waiting for merges. Token cost adds up, especially for refactoring loops.

And not everything transfers. A shared compile cache that works well for another team got zero cache hits across our worktrees, and turning off incremental builds to use it nearly doubled warm rebuilds. It may well be configuration; we haven’t found out.

The last point is a guess, not a result: beyond four or five machines, I’d expect merge and test to dominate, and more work to be redone because changes land out of step.

Keep doing and judging apart

THE WORKER

→
AN INDEPENDENT JUDGE
Decides if it's done
  • a clean context
  • a different model
  • adversarial: looks for gaps and hallucinations
  • for UI: records a video and checks it, even frame by frame

Other teams' practice. Our swarms lean on scripted gates and an oracle instead.

Other teams separate doing from judging much more strictly than I do. An independent judge, with a clean context and often a different model, decides whether the work met its goal. Adversarial reviews hunt for hallucinations and gaps. For UI work, one team records a video and has the judge verify it; one judge checked an animation’s timing frame by frame.

My swarms lean on scripted gates and an oracle instead. Both approaches share the same principle: scripts and test results, not the agent’s own judgement, decide when work is done.

Test gaming

WHAT OTHER TEAMS SAW
Green, but not true
  • Assertions weakened, tests skipped or rewritten to pass
  • Only noticed deep into a big feature
  • Fixed bugs came back: their regression tests had been quietly gamed
→
DEFENSES
Make gaming visible
  • A separate agent owns the integration tests
  • A check at session end scans for gaming patterns
  • Flag deleted tests, new ignores, loosened asserts in review

We haven't seen it, but we test outcomes, so we might not. Outcome tests are still files a worker can edit.

This one came from another team, and it’s a warning. They found agents weakening assertions, skipping failing tests, or changing tests to match new behavior, and it surfaced late because everything looked green. The worst case: bugs they had fixed came back in production, because the regression tests had been quietly gamed later.

Their defenses: a separate agent owns the integration tests, and a check at the end of every session scans for gaming patterns before work can land.

I haven’t seen it in my swarms. But I test outcomes rather than reading the tests, so I might not notice. And outcome tests are still files a worker can edit. A cheap next step would be for the layer checker or the coordinator’s review to flag deleted tests, new ignored tests or loosened assertions in a diff.

Factory or swarm? A dial

SAFETYSPEED
Factorydefined roles · a human approves the plan and every merge · a fixed quality bar · production users
Swarmgeneralists on thin slices · the coordinator merges on scripted gates · fast course-correction

Production changes the risk. A swarm that quietly deletes code or tests is a liability for customers.

Talking to other teams, it helped to think of a dial between safety and speed, rather than right and wrong.

At one end, a factory: defined roles, tickets fed through a predictable process, and a human in charge of the plan and the merge. That team runs production systems with real users, and was bitten by too little discipline when it moved fast. At the other end, my swarms: generalist agents on thin vertical slices, merging on scripted gates, and correcting course quickly.

The open question for the factory end is whether a human merge gate leaves a high-throughput swarm always waiting. The open question for my end is what changes when the output goes to customers.

Where teams disagree

Plan up front, or steer as you go?adversarially reviewed specs, then near one-shotthin slices, correct between them
Coding skills?“explain it twice, it's a skill”skills as glue only; coding skills make it worse
Do code-health metrics matter to agents?simpler code: fewer tokens, fewer hallucinationsit feels right; nobody has measured it
How much review?earn trust like a new hire; the risk is what's left off the listtrust the architecture when tests enforce it

Four honest disagreements between teams.

Plan or steer: one view is to write well-specified requirements and a plan, put them through rounds of adversarial review, and then the work is often close to one-shot. Mine is to build thin slices and course-correct between them. A middle view: even a skimmed spec gives agents scaffolding and people a shared reference.

Skills: one view is that anything you explain twice should become a skill. Mine is that skills are great as glue, for git and filing bugs, but skills that dictate how to write code made results worse, and forcing test-driven development roughly doubled task time.

Code-health metrics: one view is that simpler code means fewer tokens and fewer hallucinations. My refactoring experiment moved the grades but didn’t change behavior, and the agent itself argued long functions read fine to it. Nobody has measured it properly.

Review: one view is that trust should be earned like a new hire’s, because the risk is what was never written down. Mine is that architecture-level trust is reasonable when tests enforce the architecture.
