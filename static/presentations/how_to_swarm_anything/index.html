The brief is deliberately too large

THE WORKED EXAMPLE

Build a native, cross-platform image editor with Photoshop-scale breadth.

~540klines of Rust
25library crates
8,000+tests

PhotoCraft is a useful test because the brief is unreasonable for one person or one agent. A serious image editor needs a document model, PSD fidelity, color management, painting, text, vectors, GPU rendering, automation, platform packaging, and a large, familiar UI.

The interesting result is not that agents can type half a million lines. It is that the repository can absorb parallel work without turning those lines into an unmaintainable pile.

Less private context. Fewer invented conventions.

The first artifact is the most important one. AGENTS.md is not a welcome note. It is the operating system for contributors and agents.

It tells a worker what to read, how to pick work, what must never happen, which files are shared, how to validate a change, and how to leave the repository for the next worker. That turns tacit maintainer knowledge into versioned project state.

It is deliberately specific. “Everything is a command,” “never panic on input,” and “new behavior goes in a new module” are stronger than general advice about writing good code. Source: AGENTS.md.

A crate may only depend downward.

cargo xtask layers checks the rule. The diagram is not a suggestion.

An agent can own a layer without learning the whole application.

Parallel work needs boundaries that a machine can enforce. PhotoCraft has explicit crate layers. Foundation code sits at the bottom, then the document model, algorithms, composition, I/O, engine, and finally UI and automation.

The xtask layers command checks that dependencies only point downward. An agent working on a codec cannot quietly pull UI types into the format layer. The architectural map therefore doubles as a map of safe ownership.

The menu catalog is a surprisingly powerful planning artifact. It records the whole target menu structure with a stable command ID for every item.

When the engine registers that ID, the menu item becomes live automatically. The agent implementing Gaussian Blur does not also need to understand menu construction, shortcuts, automation, and parity reporting. One identifier joins those systems.

The generated parity document currently reports 631 of 631 menu items live, and a test prevents the floor from falling. That is breadth, not proof of full behavioral depth, which matters later. Sources: menu catalog, parity floor, generated parity report.

Four clients. One behavior. One undo step.

“Everything is a command” is the central design choice. A command carries its stable ID, label, menu path, shortcut, parameter description, precondition, implementation, and whether it belongs in the journal.

The desktop UI, CLI, MCP server, control channel, recorded actions, and plug-ins all converge on the same registry. That removes duplicate behavior and gives agents a structured way to discover what exists.

A UI gesture ends in a command too. The command owns the edit and therefore the undo boundary. Source: command registry.

Strategy becomes a queue. The queue becomes evidence.

The work queue is also kept in the repository. ROADMAP.md says where the product is. docs/gaps.md ranks the known shortfalls. The scorecard sources attach a status, issue, and code evidence to individual capabilities and performance budgets.

An agent can choose useful work without a meeting. More importantly, it can update the same artifact when the change lands. CI regenerates the scorecard and fails if the report is stale.

This is how the swarm avoids optimizing for whatever task happens to be easiest to prompt. Sources: roadmap, ranked gaps, scorecard.

There is no magical conductor in the middle. The repository coordinates the swarm.

Agents use separate build directories, own narrow file sets, add behavior in new command modules, and keep edits to shared registries small. The shared artifacts tell each worker what matters and what “finished” means.

This is closer to a well-designed distributed system than a group chat. Workers do not need to know everything the others know. They need stable contracts and low-conflict places to write. Source: parallel-agent rules.

Vertical slices keep merges boring

01Choose one visible gap“Add Gaussian Blur”
02Add one command modulegaussian_blur_cmds.rs
03Reuse the lower layeralgo::blur::gaussian
04Prove failure and successbad params · pixels · undo
05Raise the evidenceparity · scorecard · dev log

The unit of parallel work is a vertical slice, not an abstract layer. A useful slice starts with a visible gap, adds one command, reuses or extends a lower-level algorithm, proves both success and graceful failure, and updates the evidence.

That shape is easy to review and easy to merge. It avoids the classic swarm failure where one agent builds a framework, another builds a UI, and neither quite matches the other.

The shared command registry still needs a small edit, but the implementation stays in a new module. Source: contributor checklist, agent rules.

Photoshop becomes a test oracle

difference ≤ 2 / 255
ARTIFACT · TEST CORPUS

The target application supplies the expected pixels.

  1. Build a document in Photoshop
  2. Keep its flattened compatibility image
  3. Render it with PhotoCraft's CPU compositor
  4. Compare, then raise a floor that cannot fall

Natural-language acceptance criteria are not enough for compositing. PhotoCraft uses Photoshop-authored PSD files as test oracles.

The files contain Photoshop’s flattened compatibility image. PhotoCraft renders the document through its CPU compositor and compares the pixels, normally allowing at most two levels of difference out of 255. The GPU compositor is then checked against the CPU reference.

Pass counts have floors. When a fix raises one, later changes are not allowed to lower it. The target product has been turned into durable evidence instead of a vague visual reference. Sources: corpus rules, I/O corpus tests.

A bug report can be a runnable script.

Agents are not restricted to editing source and hoping. They can operate the product headlessly through the CLI and MCP, or drive the live desktop app through the control channel.

The tools expose the command catalog, current preconditions, document state, rendered previews, UI state, pointer input, and screenshots. The file authority is capability-scoped rather than ambient.

That creates a closed loop: inspect, act, see, correct. It also makes a bug report executable. The reproduction can be a short sequence of commands rather than a paragraph describing where somebody clicked. Sources: MCP conventions, control protocol.

Rust is not just a speed choice here. It lets the project keep the engine, native interface, command-line tools, automation server, and browser build in one language and one type system.

The ownership model and explicit error types support the project’s “never crash on input” rule. They do not make correctness automatic, but they make hidden sharing and unchecked failure harder to introduce across agent boundaries.

Performance work remains direct: Rayon handles CPU-parallel tiles and wgpu handles the GPU. The same core compiles to WebAssembly. The workspace forbids unsafe code, with one isolated tablet-input exception documented in the agent guide. Sources: workspace manifest, architecture, development guide.

Agents are allowed to be fast because the borders are strict.

The system expects agents to make mistakes. Quality comes from gates at the borders, not from assuming every worker has perfect judgment.

Formatting removes stylistic debate. Clippy denies dangerous shortcuts. Tests cover local behavior and real files. The layer checker preserves architecture. The Wasm build catches accidental platform coupling. The generated scorecard catches stale claims.

The full gate is expensive, so agents run narrow checks while iterating and the complete relevant set before finishing. Sources: CI workflow, development guide.

This slide is important because swarm speed can create a convincing surface before the depth is ready.

The menu is completely live, yet the project’s own roadmap estimates readiness for real work at roughly 45 percent. The scorecard records only 3 of 56 performance scenarios within budget in its current baseline, with many missing, unmeasured, or over budget.

The honest numbers are a feature of the system. They stop broad coverage from being mistaken for a finished product and give the next wave of agents something concrete to improve. Sources: roadmap, scorecard.

A reusable swarm recipe

01Write the operating manualPut judgment, constraints, and finish criteria in the repository.
02Turn the product into stable contractsCommands, schemas, crate seams, and file ownership.
03Turn ambition into a ranked queueRoadmap, gaps, budgets, and evidence.
04Give workers a closed loopInspect, act, observe, test, and recover without a human relay.
05Make truth harder to fakeGenerated reports, regression floors, oracles, and honest gaps.

The swarm scales when the work is legible.

PhotoCraft’s recipe transfers well beyond image editing.

Start with an operating manual that contains real project judgment. Define stable contracts that create low-conflict ownership. Convert the product vision into a ranked queue with measurable evidence. Give workers the tools to operate and observe the system themselves. Finally, make the truth difficult to fake with generated reports, floors, and external oracles.

The reusable idea is simple: the swarm scales when the work is legible. Agents do not need a larger prompt. They need a repository that can explain itself, constrain change, and verify the result.
