REPOSITORYthe shared model of reality

The interesting swarm problems are too large for one worker to understand at once. They cross subsystems, platforms, tools, and definitions of done.

The trick is not to give every agent more context. The trick is to arrange the repository so that each agent needs less context, while the finished pieces still compose into one product.

This is an architectural problem before it is a prompting problem.

The prompt is part of the codebase.

Every worker starts with the same map, rules, and definition of done.

Less private context. Fewer invented conventions.

The first artifact is the operating manual. AGENTS.md is not a welcome note. It records how work is chosen, where code belongs, which files are shared, how changes are validated, and what a clean handoff looks like.

That moves maintainer judgment out of private conversations and into versioned project state. Every worker begins with the same rules, and the rules evolve with the software.

Specific instructions beat vague encouragement. “Dependencies point down” and “new behavior gets a new module” are useful. “Write good code” is not.

ARTIFACT · architecture.md

Dependencies may only point downward.

check-layers enforces the rule. The diagram is not a suggestion.

A worker can own one region without learning the entire system.

Parallel work needs boundaries that a machine can enforce. The architecture document describes layers, allowed dependencies, public seams, and ownership zones.

A layer checker turns the diagram into a rule. A worker changing storage cannot quietly reach into the interface. A worker adding a command cannot bypass the domain model.

The architecture therefore does two jobs. It keeps the software clean, and it reduces the amount of context needed to make a safe change.

Ambition becomes a measurable backlog.

A swarm needs a finite description of the product it is trying to build. The surface catalog records every user-visible capability with a stable identifier.

Those identifiers join interface, engine, automation, documentation, and tracking. When an implementation registers the identifier, every client can discover it. When it is missing, the gap remains visible.

The catalog prevents a common failure mode: lots of locally impressive work with no reliable picture of whether the product is becoming complete.

Four clients. One behavior. One undo boundary.

The command registry is the central seam. A command carries its stable ID, parameters, precondition, implementation, result, and undo behavior.

Every client converges on that registry. The interface does not contain a second implementation. The automation layer does not invent another API. Recorded actions do not bypass validation.

This makes functionality composable. It also gives agents a small, typed place to discover and extend behavior.

Strategy becomes a queue. The queue becomes evidence.

The work queue belongs in the repository too. The roadmap says where the product is going. The gaps document ranks missing behavior. Machine-readable scorecards attach status, evidence, and budgets to individual capabilities.

A worker can choose useful work without a meeting. More importantly, the same worker updates the evidence when the change lands. CI regenerates reports and rejects stale claims.

This keeps the swarm aimed at user value rather than whatever task happens to be easiest to prompt.

There is no magical conductor in the middle. The repository coordinates the swarm.

Workers use isolated workspaces, claim narrow file sets, add behavior in new modules, and keep edits to shared registries small. The shared artifacts tell each worker what matters and what finished means.

This looks more like a distributed system than a group chat. Workers do not need identical knowledge. They need stable contracts, low-conflict write paths, and a reliable shared state.

The unit of parallel work is a vertical slice, not a broad layer. A useful slice starts with one visible gap, adds one command, reuses or extends a lower-level capability, proves success and failure, and updates the evidence.

That shape is easy to review and easy to merge. It avoids the swarm failure where one worker builds a framework, another builds an interface, and neither quite matches the other.

Most files in the change are new. Shared registries receive only the smallest possible edit.

ARTIFACT · TEST CORPUS

Turn the thing you are matching into durable evidence.

  1. Capture a known-good result
  2. Run the same fixture locally
  3. Compare pixels, data, timings, or events
  4. Raise a floor that cannot fall

Natural-language acceptance criteria are rarely precise enough. A target system, file corpus, protocol trace, benchmark, or curated example can become a test oracle.

The new implementation runs the same fixture and compares its observable result. The comparison might use pixels, serialized data, events, timing budgets, or semantic output.

Pass counts and tolerances have floors. When a change improves the result, later work is not allowed to lower it. A vague reference becomes durable evidence.

A bug report can become a runnable script.

Agents should be able to operate the software, not merely edit source and hope. A small control protocol exposes the command catalog, preconditions, state, bounded previews, and interface screenshots.

The tools use the same command path as the human interface. They do not create a privileged second application hidden behind the first.

This closes the loop: inspect, act, see, correct. It also makes bug reports executable. A reproduction can be a short command sequence rather than a paragraph about where somebody clicked.

The framework does not require Rust, but Rust reinforces its ideas unusually well.

Types make command and layer seams explicit. Ownership makes sharing and mutation visible. Errors are values rather than hidden control flow. The domain, native interface, command-line tools, automation server, and browser build can live in one language and one workspace.

Rust does not make correctness automatic. It does make many accidental forms of architectural drift harder to introduce across agent boundaries.

Workers are allowed to be fast because the borders are strict.

The system expects workers to make mistakes. Quality comes from gates at the borders, not from assuming every agent has perfect judgment.

Formatting removes stylistic debate. Linting denies dangerous shortcuts. Tests cover local behavior and real fixtures. The layer checker preserves architecture. Cross-target builds expose platform coupling. Generated scorecards catch stale claims.

The complete gate can be expensive. Workers run narrow checks while iterating, then the full relevant set before handing off.

Do not let a busy swarm manufacture confidence faster than software.

Swarming can produce astonishing breadth quickly. That makes honest maturity tracking essential.

The scorecard separates existence from depth. A command may be wired and reachable while its edge cases, performance budgets, platform coverage, or recovery paths remain incomplete.

That is useful information, not an embarrassment. It prevents feature counts from being mistaken for readiness and gives the next wave of workers something concrete to improve.

A reusable swarm recipe

01Write the operating manualPut judgment, constraints, and finish criteria in the repository.
02Turn the product into stable contractsCommands, schemas, layer seams, and file ownership.
03Turn ambition into a ranked queueRoadmap, gaps, budgets, and evidence.
04Give workers a closed loopInspect, act, observe, test, and recover without a human relay.
05Make truth harder to fakeGenerated reports, regression floors, oracles, and honest gaps.

The swarm scales when the work is legible.

This approach transfers to any sufficiently large software project.

Start with the operating manual. Make architecture and product surface explicit. Give each behavior a stable command seam. Keep the ranked queue and evidence beside the code. Let workers operate the product and observe the result. Enforce quality at the borders.

The aim is not to make agents imitate a large team. It is to build a repository that makes parallel work safe, useful, and easy to verify.
